# OmniGamer: назначение и архитектура

Проверено по исходникам 2026-11-18. Состояние работ: [STATUS.md](STATUS.md). Команды: [DEVELOPMENT.md](DEVELOPMENT.md).

Актуальное поведение 2026-11-14: [Непрерывная игра и проверка опыта](CONTINUOUS_PLAY.md). Обязательный план целей и остановка после достижений отменены по уточнению владельца.

## Назначение и границы реализации

Проект должен автономно исследовать игры под Windows, комментируя происходящее от лица Omni-chan. В README перечислены LDPlayer/BlueStacks, Minecraft, RPG и платформеры. Это целевой охват, а не список подтверждённо поддержанных игр.

Реализованы захват экрана, VLM, выполнение действия, оценка изменения изображения, эпизодическая память и панель. PlaySupervisor поддерживает непрерывную самостоятельную игру, проверку before/after с HUD и короткую смену стратегии при застревании. После прохождения или достижения игра продолжается. Goal-планировщик выполняет ограниченный план навыков для CLI `--goal`; это отдельный режим. Нет обучения весов, TTS или интеграции со стриминговыми площадками.

Дополнительно реализован отдельный режим skill `approach_target`: локальный OWLv2 detector service на loopback, CLI-ветка без VLM и записи опыта, ограниченный FSM подхода, калибровка camera counts и `skill_steps.jsonl`. Это отдельный экспериментальный навык, его поведение не распространяется на обычный агент. Контракт — в [SKILLS.md](SKILLS.md), запуск и внешняя среда описаны в [DEVELOPMENT.md](DEVELOPMENT.md).

В goal-режиме после `approach_target` с причиной `blocked_after_side_step` или `target_not_reacquired` исполнитель делает одну локальную попытку до медленного VLM перепланирования: ограниченный поворот камеры, поиск цели (sweep=2), повторный подход. В самом `approach_target` после боковой коррекции выполняется профильное число jump+forward recovery (по умолчанию 1, Minecraft 2), затем — одна боковая коррекция в противоположную сторону; клавиши и длительность проверяются по профилю. Цепочка соблюдает лимиты времени, вводов, навыков и F12, события пишутся в `local_recovery_skill`. В живой попытке второй подход достиг `REACHED`, но добыча не изменила hotbar; в попытке 8 прыжок дал рост рамки 0.294, однако 51/60 вводов ушли на повороты; порог 0.1 в попытке 9 сократил циклическое переключение, но цель была потеряна; попытка 11 израсходовала 60/60 вводов без добычи. Minecraft threshold теперь 0.2 по наблюдавшемуся сдвигу около 0.185; near-REACHED дополнительно проверяет margin перекрестия (0.08 для Minecraft) и поворачивает камеру по вертикали/горизонтали. Живые прогоны подтвердили, что это пока не компенсирует переключение на близкие рамки деревьев на склоне. В постфиксной попытке 13 три удержания без шага вперёд всё ещё дали region_delta=0: REACHED по fallback-рамке дерева не гарантирует, что вертикальная ось прицела находится на стволе; сейчас нет подтверждённой модели рельефа или вертикальной привязки перед mining. Детали и кадры — в [STATUS.md](STATUS.md).

Переход к конфигурации по профилям `data/profiles/<game-id>.json` реализован для профиля ввода, движений, действий, запретов, регионов, детекторных синонимов, порогов и лимитов. CLI валидирует профиль до создания агента; dashboard загружает профиль по `game_id`. Legacy-цикл применяет profile movement/action limits и запрет клавиш, goal-планировщик ограничивает имена действий/регионов схемой из профиля. UI-геометрия включается явным `ui_adapters`; базовый шаблон её не включает. `approach_target` использует `normalized_error_per_camera_count`/`invert_horizontal` из profile calibration, когда отсутствует сохранённая per-game калибровка; прежние `camera_counts_per_radian` и `k` читаются с исторической фактической семантикой без преобразования единиц. Значение обозначает нормированный горизонтальный сдвиг рамки на один input count, а не угол в радианах. Навык также использует профильный `approach_track_max_center_shift` для отказа от рамок, резко сместившихся к соседнему объекту; порог был 0.35; после телеметрии попытки 8 с 27 скачками центра около 0.185 на 60 переходах профиль Minecraft сначала уточнён до 0.1, а после наблюдения скачков 0.185 — до 0.2; живой проверки 0.2 пока нет. Профиль Minecraft также просит делать до трёх проверяемых удержаний `primary_hold` после успешного подхода, прекращая при изменении хотбара; между повторами шаг вперёд отключён (`interaction_retry_step_seconds=0`), чтобы сохранять тот же блок под прицелом; это добавлено после живого прогона, где одного удержания 2.5 с оказалось недостаточно. Общие дискретные `look`/`turn` не масштабируются. Это подтверждает профильный путь в коде и синтетических/реальных dry-run, но не реальную универсальность по играм.

Реестр навыков `omnigamer/skills/registry.py` описывает шесть `SkillSpec` с JSON Schema параметров. `approach_target` и базовые функции в `skills/basic.py` возвращают общий `SkillResult`; `SkillStepRecorder` и `ApproachTargetRecorder` пишут версионированный `skill_steps.jsonl`, а `summarize_run.py` считает финальные статусы по навыкам. CLI использует реестр через `--goal`; legacy-цикл выбирается только `--legacy`, а `--dry-run` пишет `would_send` без ввода.

Срез 2026-11-15: `omnigamer/planner.py` проверяет до шести goal-шагов по реестру, схемам и profile actions/regions; невалидный ответ получает одну повторную попытку. Goal output ограничен конфигом `goal_plan_max_tokens=256` (default); на сохранённом Stage 8 кадре валидный трёхшаговый план получен за 86.06 с после timeout живого запроса на старом лимите. Запрос предпочитает краткий план из 1–3 шагов, но строгая schema остаётся. В CLI `--goal` `motion_limits.max_actions` ограничивает суммарные control-вызовы, отдельно от `goal_max_skill_steps`; `input_action_budget` записывает фактический счётчик, не включая release. Legacy выбирается только через `--legacy`, а `--dry-run` пишет `would_send` без ввода и держит память в SQLite `:memory:`. `tests/sim/` проверяет путь на двух синтетических профилях. `omnigamer/doctor.py` выполняет read-only диагностику, включая доступ к active input desktop без `SendInput`; `start_all`/`stop_all` принимают пути сервисов из переменных окружения. Реальный Stage 8 пройден: doctor, десять планов на пяти сохранённых кадрах, CLI replay и dry-run реального VLM-плана через синтетический capture/detector. Артефакты и ограничения перечислены в [STATUS.md](STATUS.md).

Актуальный срез 2026-11-18: GoalPlanner ограничивает навыки по профильной геометрии меню, валидирует immediate postcondition перехода из главного меню и отвергает повтор плана, ведущий к игровому состоянию вместо списка миров. Перед каждым навыком GoalExecutor повторно проверяет свежий кадр, а mining-взаимодействие пропускает только для явно перечисленного в mine_actions действия после уверенного профильного preflight; общий бюджет и deadlines оборачивают контроллер и detector. click_menu_target локализует запрос через screen-only VLM grounding и проверяет неизменность участка цели до клика. Запись play_lesson перепроверяет status, пару check, общую session, строгий порядок step, candidate_step и совпадение action с `visual_checks.action_json` у границы SQLite. Полный синтетический suite — 355 тестов; он проходит и при пустом runtime profile directory. Последний успешный live dry-run выбрал «Одиночная игра» и не отправил ввод; последующая проба компактной JSON-схемы была отвергнута из-за несовпадения candidate/bbox и изменения откатили. Read-only doctor подтвердил VLM/detector, но OpenInputDesktop вернул WinError 5. Реальный клик, переход в мир и успешная добыча не подтверждены.

## Поток одного шага

1. `OmniAgent.step()` увеличивает счётчик, фокусирует выбранное окно и проверяет foreground, получает RGB-кадр через `WindowCapture` и вычисляет dHash. Ненулевой невалидный HWND и отказ фокусировки приводят к ошибке, без захвата другого приложения.
2. `GameMemory.get_learning_context()` извлекает опыт только выбранной игры: сводку действий на похожих экранах и последние четыре эпизода, включая предыдущие запуски. Последние десять действий восстанавливаются из БД при создании агента/смене профиля.
3. `VisionBrain.decide()` уменьшает кадр до config.image_max_size (640), кодирует JPEG quality=85 в data URI и делает синхронный HTTP POST к OpenAI-совместимому chat completions endpoint.
4. Модель получает SYSTEM_PROMPT, текущий кадр, ограниченную сводку опыта и отдельный необязательный блок Current goal из CLI `--goal`/поля панели. Полная БД и предыдущие изображения в запрос не передаются. Параметры legacy-решения: temperature=0.3, max_tokens=config.vlm_max_tokens (192); общий HTTP timeout — 110 с. Goal-план ограничен шестью шагами и config.goal_plan_max_tokens (256 по умолчанию); допустимые profile action/region перечислены в schema. Click/drag используют экранные координаты; look задаётся только перечислениями `look_direction` и `look_amount`, преобразуемыми в counts в `omnigamer/look.py`.
5. Ответ HTTP-пути ограничен JSON schema llama.cpp с обязательными полями восприятия, намерения и look-параметров; look с невалидным направлением/величиной получает один повтор решения, затем безопасный wait с явным refusal reason. Другой невалидный ответ не извлекается regex-ом в действие. При ошибке клиента агент обнаруживает fallback и прерывает шаг до ввода/записи опыта. Две последние неэффективные попытки того же действия на точном хэше вызывают один запрос перепланирования. Для двух последних одинаковых неэффективных click/double_click дополнительно проверяется сходство thumbnail без требования совпадения dHash — для анимированных меню. Если повтор сохраняется, выполняется wait с learnable=0.
6. Перед вводом агент проверяет видимость (window) либо фокусирует окно (native), затем сверяет геометрию. Контроллер проверяет цель и failsafe, пытается отпускать ввод в finally; window использует PostMessage, native — SendInput/SetCursorPos. Глобальный `emergency_key` (по умолчанию F12) опрашивается через `GetAsyncKeyState`, защёлкивает stop-флаг и отпускает удерживаемые агентом кнопки. Решения и оценки VLM выполняются в daemon worker, поэтому агент прекращает ждать запрос при остановке, хотя HTTP-запрос внутри сервера не отменяется. Затем пауза `config.action_delay_seconds` (0.1 с), проверка цели выбранного backend, второй кадр и оценка дельты. Ошибка исполнения не записывается как опыт; last_error доступен через state. Для walk/jump длительность ограничена диапазоном 0.5..config.max_motion_seconds (0.75 с). Mine/wait/key/drag не получают это ограничение.
7. При дельте ≥0.06 effective означает только изменение экрана. CameraGuard ограничивает команды и блокирует неподтверждённое копание. Look/wait маркируются `camera_motion`, не считаются effective/learnable и по умолчанию не вызывают VLM-проверку результата (`assess_look_with_vlm=False`). Повтор dHash (последние 8 состояний, расстояние ≤4) или look A-B-A-B записываются в telemetry и запускают четырёхшаговую смену стратегии. PlaySupervisor подтверждает другие наблюдаемые результаты двумя проверками, не останавливая игру. Через 20 попыток/90 активных секунд без проверенного продвижения также включается восстановление.

Телеметрия записывает JSONL по шагам, ресурсам и подмешанному контексту в `data/runs/<run_id>/`, выборочные кадры — в `frames/`. `steps.jsonl` хранит raw JSON попыток, финальное действие, причины отказа, срабатывания повторов и тайминги/типы HTTP-запросов. Она не меняет политику действий; формат и отчёт описаны в [TELEMETRY.md](TELEMETRY.md).

Fallback VLM/визуальной проверки записывается ERROR-логом с traceback и причиной в `decision.fallback_reason` строки шага; `summarize_run.py` считает такие шаги. RAM процесса Windows снимается через PSAPI с явными WinAPI-сигнатурами и `PROCESS_MEMORY_COUNTERS_EX`; ошибка выборки даёт `null` и однократный ERROR-лог на поток.

CLI и dashboard настраивают stdout/stderr как UTF-8 с `errors=replace` до вывода; Rich-консоль создаётся после настройки. Ошибки косметической печати перехватываются с одним WARNING. CLI начинает запись до привязки окна; необработанные ошибки цикла/привязки сохраняют `ended_at`, `termination_reason=error` и короткое поле `error` в run_meta, останавливают sampler и выпускают удерживаемый ввод.

`last_frame` содержит кадр ДО действия; `/api/frame.jpg` сохраняет этот диагностический кадр с оверлеем. Основное изображение панели загружается отдельно из `/api/live.jpg` каждые 500 мс, не дожидаясь решения модели. Живой preview не вызывает focus/step и не передаёт каждый свой кадр в VLM; перед следующим решением агент захватывает собственный новый кадр. Preview требует видимости без перекрытия в window-режиме или foreground в native; при нарушении возвращает ошибку. Счётчик шагов сбрасывается при создании агента; идентификатор сессии в имени снимка исключает перезапись файлов предыдущего запуска. Архив скриншотов по-прежнему записывается раз в завершённый шаг, не каждые 500 мс.

## Контракт действий

BrainDecision дополнен scene_type, camera_pitch, visual_confidence. Duration ограничен (0,10], confidence/visual_confidence — [0,1], нечисловые бесконечные значения не разрешаются. Парсер отклоняет неизвестное действие; для click/double_click обязательны x/y, для drag также x2/y2, конечные координаты 0..1000. Явные доли 0..1 масштабируются, смешанные единицы отклоняются, нативные дробные значения округляются. Look остаётся относительными counts без масштабирования; перед исполнением CameraGuard ограничивает команды, исправляет пустой поворот и экстремальный наклон.

| Действие | Используемые параметры | Исполнение |
| --- | --- | --- |
| click, double_click | x, y: 0..1000 | Клиентские координаты → экранные пиксели |
| drag | x, y, x2, y2: 0..1000; duration | Перетаскивание левой кнопкой |
| look | look_direction=left/right/up/down, look_amount=small/medium/large | В `omnigamer/look.py` переводится в относительные counts; native=SendInput, window отклоняет look |
| walk | key: w/a/s/d (по умолчанию w), duration 0.5..0.75 | Удержание одной клавиши; x/y не вращают камеру |
| mine | duration ≥ 1.0 | Удержание левой кнопки в текущей позиции |
| use | — | Правый клик в текущей позиции |
| jump | key: w/a/s/d (по умолчанию w), duration 0.5..0.75 | Одновременное удержание направления и Space; key=space от старой модели нормализуется в w. Для прыжка на месте: key action со space |
| key | key, duration | Scan code либо VK fallback |
| wait | duration | Синхронный sleep |

Полный список клавиш задан в `SCAN_CODES` и `VK_MAP` в controls.py. Неизвестные клавиши вызывают ValueError, а не учитываются как выполненное действие.

`press_keys()` валидирует все клавиши до ввода и удерживает их через ExitStack: при ошибке/потере фокуса пытается отпустить все уже нажатые клавиши в обратном порядке. `move_camera()` отправляет знаковые относительные пакеты; значение x/y — counts, не градусы, чувствительность определяется настройками игры. Реальная калибровка угла не реализована.

## Захват и ввод

Список окон формируется через pywin32: сначала default desktop, при отсутствии результата — EnumWindows. Отбираются видимые окна с заголовком и размерами >100×100. Поиск по подстроке возвращает первое совпадение в отсортированном списке.

MSS захватывает экранный прямоугольник клиентской области, а не скрытый framebuffer окна. По разрешению владельца стартовый backend теперь native (общий ввод для рабочей камеры). Альтернативный window-backend проверяет видимость/перекрытие и отправляет PostMessage в HWND без фокусировки, SendInput и перемещения системной мыши. Скрытое/свёрнутое окно не поддерживается. Альтернативный native-backend вызывает `focus()` при attach/перед кадром/перед вводом и использует общий SendInput с foreground-проверками. Автоматического переключения нет. Raw Input и собственный захват курсора игрой не изолированы; полный независимый ввод в 3D требует отдельной сессии/VM. Для каждого кадра MSS создаётся и закрывается в вызывающем потоке.

`pointer.py` — логический розовый AI-курсор и неактивирующий click-through overlay, исключённый из захвата. `window_input.py` — адресованный оконный ввод. Живой кадр панели получает отдельный маркер после захвата. Подробнее: [POINTER_AND_MENU_MEMORY.md](POINTER_AND_MENU_MEMORY.md).

`last_rect` кэшируется захватом, включая случай первого монитора; `norm_to_screen()` использует его. При изменении положения/размера окна за время инференса шаг отменяется, чтобы не применять устаревшие координаты. Гонка с ручным переключением окон полностью не устранена.

## Память

`MenuMemory` (`menu_memory.py`) хранит `menu_actions`: проверенные рёбра меню по game_id, точное состояние выбора, параметры действия, якорь кнопки, две visual_checks и счётчики. Обучение требует post с явным menu_action_succeeded и menu_confirm следующего наблюдения. При распознавании уверенность ≥0.85, состояние/якорь должны совпасть; граф ищет путь до игры до четырёх переходов, исполняется только первый шаг. Неудачный повтор отключается до переосвоения. Это эпизодическая память, а не обучение весов; модель может ошибаться, в том числе не суметь освоить меню.

`GameMemory` открывает и явно закрывает SQLite-соединение на каждую операцию. `_init_db()` создаёт таблицы и выполняет повторяемую аддитивную миграцию без удаления существующих строк:

- `experiences`: исходные id, timestamp, state_hash, action_type, x, y, key, screen_delta, effective, commentary, intent; новые game_id, next_state_hash, duration, x2/y2, observation, session_id, visual_signature, learnable. Индексы по профилю/состоянию и профилю/id.
- `dead_clicks`: старая таблица сохранена для совместимости. Старый get_dead_click_hints доступен, но новый агент извлекает подсказки из experiences с учётом профиля и последующих изменивших экран попыток.

Миграция supervisor добавила к experiences goal_id, outcome_status, assessment_json, action_source, confidence, timings_json, policy_version и таблицы agent_state, visual_checks, goal_lessons, failed_attempts. Непрерывный режим добавляет play_lessons; у новых experiences goal_id=NULL, policy_version=3. Старые goal_lessons сохраняются для аудита, их валидатор GoalSupervisor не управляет живым агентом. Сырые observation/intent не подставляются как факты. Контракт — в [CONTINUOUS_PLAY.md](CONTINUOUS_PLAY.md).

dHash: grayscale 9×8, сравнение соседних столбцов, 64 бита, строка из 16 hex-символов. Дельта: средняя абсолютная разность grayscale-кадров 64×64 / 255. Поиск: Hamming distance ≤ config.memory_hash_distance (по умолчанию 4), максимум восемь хэшей и 40 последних записей каждого. Дополнительный фильтр: RGB-thumbnail 8×8, средняя разность ≤0.08 и разница пропорций ≤5%. Это визуальная эвристика, не семантическое распознавание состояния.

Сводка передаёт до шести групп действий и четырёх недавних эпизодов, с усечёнными описаниями. Действия группируются по типу, параметрам, координатам с шагом 50 и длительности с шагом 0.5 с; для drag учитывается конец. Look/wait исключены из похожего опыта и свежей истории промта, даже если старые строки SQLite содержат такие действия. Wait и learnable=0 не используются как кандидаты изученных действий. Записи не превращаются в утверждения о достижении игровой цели.

`get_navigation_hint()` отдельно проверяет два последних learnable walk в одном направлении: оба effective=0, screen_delta ≤ navigation_stuck_delta (0.015) и thumbnail похожи на текущий. Тогда в запрос добавляется совет проверить уступ/стену, попробовать jump/look/другое направление. Если модель повторяет то же walk, выполняется один запрос перепланирования. При повторном игнорировании агент делает look right/large, action_source=navigation_recovery. Это эвристика осмотра, а не пространственная карта или доказательство препятствия.

Профиль: явное имя нормализуется в `game:имя`; без него используется `window:заголовок`, либо `monitor:primary` без окна. Указывай стабильное имя через поле панели или CLI `--game-id`, особенно если заголовок игры меняется. Один профиль не следует использовать для разных игр/режимов. Старые записи мигрируют в `legacy` и автоматически в новые профили не подмешиваются: их игру определить нельзя.

`get_stats(game_id)` возвращает накопительную статистику профиля: total_actions, effective_actions, success_rate, unique_screens_discovered, observed_transitions (различные before/after хэши при learnable=1 и effective=1). Без game_id метод сохраняет общую статистику для совместимости. Это не метрики игрового мастерства.

## Панель и HTTP API

FastAPI создаёт глобальный `OmniAgent` в startup. Статика монтируется на `/` после API. Все обработчики синхронные.

| Метод и путь | Назначение |
| --- | --- |
| GET /api/windows | Список окон |
| POST /api/attach | JSON `{"hwnd": 123, "game_id": "minecraft-survival"}`; меняет цель/профиль, восстанавливает историю и фокусирует окно |
| POST /api/step | Выполняет один полный шаг |
| GET /api/state | Счётчик, is_running, решение, дельта, статистика профиля, game_id, memory_context, memory_warning, last_error, timings, action_source и последние 10 реплик |
| GET /api/frame.jpg | Последний кадр с оверлеем; заглушка до первого шага |
| GET /api/live.jpg | Свежий JPEG до 960 px с AI-указателем, без focus/шага; проверяет видимость (window) либо foreground (native); Cache-Control=no-store |
| POST /api/input-backend | Явный выбор window/native, сериализован с шагом, без автозапуска |

State возвращает supervision (режим исследования/восстановления и счётчики опыта), assessment, assessment_error, guard_reason; timings — verification_seconds; stats — checked_play_outcomes и failed_attempts. Невыбранное окно запрещает step. Нет назначения обязательной цели через API/панель; успех и застревание не завершают игру. Ошибки выполнения и failsafe сохраняют остановку.

Автоигра реализована в браузере: последовательные `/api/step`, целевой интервал между началами шагов выбирается как 1000 или 500 мс. После ответа ожидается max(0, target-elapsed), дополнительные 1500 мс убраны. Цель не гарантирует реальную частоту: медленный инференс/действие удлиняет цикл, следующий запрос не отправляется параллельно предыдущему. State и живой preview обновляются отдельно каждые 500 мс, для preview допускается один запрос в полёте. Timings показывают vision_seconds (включая перепланирование), action_seconds и total_seconds завершённого шага. «Стоп» отменяет будущие вызовы, текущий запрос продолжается; F12 отдельно прерывает текущий шаг и освобождает ввод. HTTP/сетевые ошибки шага останавливают автоцикл; ошибки исполнения RuntimeError/InterruptedError/ValueError возвращаются как HTTP 409. is_running по-прежнему отражает только CLI. RLock сериализует шаги и attach. State/frame не являются атомарным snapshot. Профиль сохраняется в localStorage, применяется кнопкой привязки; в панели раскрывается последний контекст памяти.

## Конфигурация

`config.py` содержит singleton `config`, настройки не читаются автоматически из `.env` или переменных окружения. Каталоги данных создаются при импорте. Основные пути вычисляются от исходников, но VLM debug-логи жёстко привязаны к `D:/OmniGamer/data/`, а bat-файлы — к конкретной машине. Dashboard по умолчанию слушает только `127.0.0.1`; другой bind задаётся аргументом `--host`.

Неиспользуемые `target_window_title`, `target_hwnd` и `personality_prompt` удалены из global config после поиска ссылок. `project_root` выбирает каталог профилей; `data_dir` используется телеметрией и диагностикой; `screenshots_dir` — при включённом сохранении кадров. `emergency_key` управляет глобальным Windows polling аварийной клавиши. `request_timeout` (110 с), `image_max_size`, `vlm_model_name` и `vlm_max_tokens` передаются агентом в VisionBrain. Общий prompt находится в `vision_brain.SYSTEM_PROMPT` и собирается с профилем в `_system_prompt(profile)`.

## Актуальные исправления ввода/меню 2026-11-14

Native включён по прямому разрешению владельца, AI-маркер сохраняется. Window look явно не поддерживается и прерывается до отправки фиктивных команд. После native look camera_feedback.py сопоставляет области кадра и показывает наблюдаемое смещение либо отсутствие подтверждения; это не проверка игрового прогресса.

vision_brain.py использует JSON schema llama.cpp, обязательное восприятие/намерение и повторную локализацию click/double_click. ui_grounding.py измеряет кнопки по пикселям и имеет специальный адаптер узнаваемой раскладки world_select. Акторные координаты клика не исполняются напрямую. Пост-проверка неизвестного click также считается меню-проверкой; успешное назначение читается без подсказки намерения. Источники evidence_source различают visual_model, visual_model_with_geometry и screen_geometry; последний используется для рамки выбранной строки + включения Play с последующим новым подтверждением. Полный контракт и ограничения — [POINTER_AND_MENU_MEMORY.md](POINTER_AND_MENU_MEMORY.md).

Профиль по заголовку Minecraft исключает суффикс статуса после ` - `, чтобы вход в одиночный мир не создавал новую память. Для разных игр/режимов используйте явный game_id. Native-камера проверена реальным ограниченным вводом; устойчивость длительной игры не подтверждена.
