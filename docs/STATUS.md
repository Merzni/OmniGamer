# Текущее состояние

## Экранная геометрия главного меню (2026-11-18)

На кадре Minecraft `1600×877` локальный детектор кнопок нашёл три центральные широкие кнопки раздельно. Профиль явно включает общий `stacked_main_menu` геометрический адаптер: он подтверждает `menu/main_menu/default`, если VLM вернул `unknown` или `menu` и на кадре есть три выровненные центральные кнопки плюс пара нижних кнопок. Это шаблон UI-геометрии, не игровая логика; прочие профили его не включают. Первый read-only `ground_click` завершился за 58.14 с с уверенностью 0.95 и точкой `(530,438)` внутри измеренной третьей кнопки; модель вернула ожидаемый `world_select`. В серверном журнале для этого запроса: 57.04 с, 97 выходных токенов, 2.89 токена/с. Затем `click_menu_target` повторно локализовал ту же метку с уверенностью 0.95 и отправил один оконный `PostMessage` клик `(848,407)`. Навык вернул `UNCONFIRMED`; свежий кадр остался на title menu, поэтому переход не засчитан. Тот запрос занял 62.17 с, 113 выходных токенов, 2.93 токена/с. `WindowCapture.focus()` после этого завершился `Game window lost focus`; `GetForegroundWindow=0`, native-клик не посылался. Кадр окна читается, окно видимо и не свёрнуто. После добавления адаптера полный набор выявил запрет на Minecraft-специфичные термины в ядре, поэтому тип и геометрический matcher обобщены. После обобщения полный набор: 289 тестов прошло; `pyflakes` без замечаний.

## Проверка свежести menu-target перед вводом (2026-11-18)

`click_menu_target` ожидал медленную VLM-локализацию, затем проверял фокус и геометрию окна, но не проверял целевую область после запроса. Экран мог перейти на другой menu за время инференса, оставив координату устаревшей. Теперь навык получает новый кадр непосредственно перед вводом и сравнивает локальную область вокруг grounded-точки с исходным кадром; при изменении target или размера кадра click отменяется. Изменения вне локальной области (например, Minecraft background panorama) не отменяют действие. На двух сохранённых Minecraft title-menu кадрах измеренная разница grayscale для target-региона равна нулю при анимированном фоне. Регрессии: изменённый target отменяет ввод, изменение за пределами области разрешает действие. Полный набор: 291 тест прошёл; `pyflakes` чист. Live menu-click с этим свежим экранным guard пока не повторён, так как Minecraft не удалось активировать через штатный `WindowCapture.focus()` и foreground guard отменил попытку до ввода.

## Goal-навык для экранного меню (2026-11-18)

В live-диагностике Minecraft VLM трижды не локализовала кнопку в goal-цикле; в отдельном dry-run планировщик предложил `interact_until_change` по региону `hotbar` с `interact` (правая кнопка). Этот план был просмотрен и не исполнялся. Причина на уровне контракта: реестр не имел навыка экранного клика по меню и описывал только region/action-взаимодействие.

Добавлен `click_menu_target` только для профилей с `ui_adapters`. Planner требует, чтобы `expected_result` в args совпадал с postcondition шага; prompt требует точный control, непосредственно ведущий к пользовательской цели. Навык захватывает свежий кадр, запрашивает существующий `ground_click` с ограничением HTTP timeout, требует verified `menu`, уверенность не ниже 0.85, валидные координаты, неизменную геометрию окна и текущий target/focus guard; затем отправляет ровно один левый клик через контроллер выбранного backend. Для известных переходов `world_select`, `world_selected`, `gameplay` runtime также блокирует расхождение ожидания и UI-адаптера. Клик расходует общий input-action budget. GoalExecutor оценивает новое состояние по `expected_result` и `success_check`, и не считает одну отправку клика успехом. В prompt добавлено правило выбирать этот навык для меню и не применять gameplay-навыки.

Добавлены unit-регрессии на отправку ровно одного клика, отказ до ввода при неверной сцене или несовпадающем переходе адаптера, отмену при изменении геометрии окна, общий budget, соответствие postcondition и обязательный verifier. Финальный полный набор: 286 unittest прошли, pyflakes без замечаний.

Три live dry-run с нулём вводов: первый план выбрал `Minecraft Realms` для одиночного мира; два последующих после уточнения контракта предложили `Одиночная игра` с `expected_result="World selection screen appears"`. Ограниченный живой запуск через `native` остановился до inference, потому что Windows не позволила перевести Minecraft в foreground. Запуск через addressed `window` backend прошёл attach, но планирование завершилось HTTP `ReadTimeout`; фактически посланных вводов 0/1. На повторной проверке оба сервиса отвечали HTTP 200. Успешное исполнение нового grounding-контракта и перехода в меню миров пока не подтверждены.

Обнаруженный HTTP timeout больше не пробрасывается из goal-планировщика как необработанный traceback: `GoalPlanner` превращает исключение запроса в `PlanningError` с исходным типом/сообщением, сохраняет длительность запроса, а `GoalExecutor` завершает прогон статусом `FAILED` до навыка/ввода. Регрессия проверяет no-input и telemetry `plan_rejected`. Живое повторение после изменения не делалось; прежний live `ReadTimeout` подтвердил сам отказ VLM, но новый graceful-result проверен offline.

Метрики выводятся только из явно записанных событий: `task_success_rate` относится к одному завершённому goal-прогону, а `DRY_RUN` исключается; `skill_success_rate` считает только `SUCCESS_VERIFIED` успешным исходом, а знаменатель берёт из результатов навыков с записанным статусом; `time_to_success` — прокси по длительности всего процесса; `vlm_calls_per_success` учитывает step HTTP-запросы и planning requests, но не скрытые проверки goal; число detector-вызовов и переключений цели текущая схема телеметрии точно не фиксирует и поэтому не подставляет нули. Синтетические регрессии проверяют агрегирование и исключение dry-run. В локальном архиве обнаружены 43 каталога прогонов: 22 завершённых goal, из них 16 `FAILED`, 6 `DRY_RUN`, ни одного `SUCCESS`; ещё 21 без `run_finish`. `SkillOutcomeStore.summary()` ограничивает сводку 20 группами и работает с ограниченным окном: последние 200 общих исходов плюс, при активной цели, последние 200 исходов этой цели. Индекс `(game_id,target,id)` поддерживает адресную выборку. Целевые группы идут перед остальными, остальные сохраняют newest-first порядок, а verified-пример всё так же фильтруется по состоянию. Тесты проходят через `GoalExecutor` и проверяют приоритет цели при заполненном лимите, совпадающий dHash и рецепт, вытесненный из глобального окна 200 более свежими записями других целей. Это исправляет отбор контекста, но не доказывает полезность рецептов для живой игры.

Read-only end-to-end replay на одном сохранённом кадре `640×321`: точный synthetic verified recipe `turn right/20` был записан до 250 неудачных исходов по другим целям. При планировании совпадающей цели и dHash recipe сохранился, локальная VLM вернула тот же skill/args, `memory_reuse_count=1`; один planning request занял 3.824 с. GoalExecutor был в dry-run, вводов 0, SQLite — `:memory:`. Это подтверждает передачу и следование примеру в одном контексте, а не качество искусственного исхода, повторяемость или игровой успех.

## Точность исходов в памяти навыков (2026-11-16)

Общий `SUCCESS` у `move_pulse` и `turn` означает, что ввод отправлен; он не доказывает эффект в игре. Ранее такой последний исход мог попасть в `verified_example` и success-rate. Теперь сводка учитывает как результат только явные коды `SUCCESS_VERIFIED`, `TARGET_DETECTED`, `APPROACH_REACHED` и `CONDITION_MET`; общий `SUCCESS` остаётся попыткой в знаменателе и отключает старый пример. Новые коды навыков поиска, приближения и ожидания отражают соответственно детекцию цели, геометрическое достижение и выполненное условие. Добавлены регрессии для подсчёта и выдачи примеров; синтетические проверки не подтверждают эффект на живой игре.

`GoalExecutor` раньше завершал план как `SUCCESS`, если каждый навык вернул успешный статус, хотя последний шаг мог только отправить ввод. Теперь финальное `expected_result`/`success_check` проверяется визуальным критиком на паре кадров; уверенный `progress` сохраняется как `SUCCESS_VERIFIED`, а без критика итог — `UNCONFIRMED`. Локальное восстановление заблокированного приближения также проходит финальную проверку. Это увеличивает число критических VLM-проверок на один финальный шаг плана; локальная задержка этой проверки ещё не измерена.

Проверка recovery-ветки выявила двойную запись результата восстановленного `approach_target`: helper сохранял командный `SUCCESS`, а `GoalExecutor` затем сохранял результат той же попытки после проверки. Запись recovery-приближения теперь принадлежит `GoalExecutor`, поэтому в истории остаются исходная неудача и один итог восстановленной попытки; тест проверяет `1/2` успехов и одну доступную подтверждённую запись.

## Аудит и исправление лимита `approach_target` (2026-11-16)

Проверка кода подтвердила, что прямой CLI-режим `--skill approach_target` проверял `max_impulses`, но увеличивал счётчик только на клавиатурных импульсах. Повороты камеры отправлялись через тот же контроллер, однако не учитывались в этом лимите. Goal-режим имел внешний `InputActionBudget`, поэтому разрыв относился к прямому режиму навыка. Исправлено: профильный бюджет теперь считает все вызовы ввода (движение, восстановление и камеру), а число движений остаётся отдельной метрикой `impulses`. Финальный `SkillResult.evidence` и записи шагов содержат `input_actions`.

Добавлена регрессия: с бюджетом в одну команду горизонтальная коррекция камеры расходует лимит, и второй ввод не отправляется. Проверка покрывает синтетические контроллер и детектор; это не игровой прогон. Полный аудит отслеживания цели, подтверждения взаимодействия, памяти навыков и задержек ещё продолжается; этот фикс сам по себе не подтверждает исправление добычи Minecraft.

В том же аудите подтверждён риск переключения цели: при нескольких допустимых рамках `_select` выбирал ближайшую по центру без проверки, насколько близок второй кандидат. Добавлены профильный порог неоднозначности и ограниченное поведение: равноправные кандидаты не перепривязывают трек и не вызывают движение; две последовательные неоднозначные детекции завершаются `UNCERTAIN`/`UNCONFIRMED`. Синтетические регрессии проверяют симметричные кандидаты, сохранение исходного центра и отсутствие слепого движения после неоднозначности. Живые кадры/сцены не использованы, поэтому оптимальность порога и точность трекинга в игре не подтверждены.

Аудит навыков взаимодействия выявил, что `interact_until_change` ранее возвращал `SUCCESS_REGION_CHANGE` только по порогу RGB-дельты, а `GoalExecutor` записывал этот исход как успешный и завершал шаг; поле плана `success_check` фактически не исполнялось. Теперь региональная дельта даёт `UNCONFIRMED/REGION_CHANGE_UNCONFIRMED`. В `--goal` перед записью исхода вызывается отдельный `VisionBrain.assess` на кадрах до/после с переданными `expected_result` и `success_check`: уверенный `progress` становится `SUCCESS_VERIFIED`, `blocked/regressed` — `FAILED`, прочие исходы и ошибки проверки остаются `UNCONFIRMED`. Без проверяющего дельта не повышается до успеха. `skill_outcomes` теперь учитывает только `SUCCESS`/`SUCCESS_VERIFIED` как успех и показывает число неопределённых попыток отдельно; старые `SUCCESS_REGION_CHANGE` читаются как неопределённые. Это одна проверка той же локальной VLM, не независимое доказательство и не гарантия причинности.

Симуляционный тест проверяет видимый маркер по изображению (синтетический критерий), а тесты планировщика покрывают отсутствие проверяющего, подтверждение, отказ, низкую уверенность, неизвестный исход и передачу оставшегося бюджета времени. Проверка добавляет VLM-запрос при срабатывании регионального порога; задержка этого вызова на локальной модели ещё не измерялась. Это не живой игровой прогон и не доказывает, что VLM надёжно распознает предметы в Minecraft.

Проверка контракта `approach_target` выявила, что fallback-синоним мог поддержать `REACHED`, даже если запрошенная детектору точная формулировка не дала рамку. Теперь fallback сохраняет пользу для поиска и наведения, но `REACHED` требует детекцию исходного запроса. Синтетический тест проверяет различие точного и широкого query; семантическая точность OWLv2 по реальной сцене не подтверждена.

Проверка повторного использования опыта показала, что `skill_outcomes` хранил только частоты по имени навыка и тексту общей цели. Теперь таблица аддитивно получает nullable `args_json`, `expected_result` и `success_check`; новые проверенные успехи показывают один последний подтверждённый пример на пару навык/цель, а неопределённые и неуспешные параметры не попадают в `verified_example`. Сводка ограничена 20 группами и передаётся планировщику, prompt просит повторять пример только при совпадении видимого состояния и цели. Добавлена миграционная регрессия со старой схемой на временной БД. Это контекстное переиспользование примеров планировщиком, не автоматическое выполнение без нового плана и проверки применимости.

OmniGamer — прототип автономного игрового агента для Windows. Он захватывает изображение выбранного окна, получает решение от локальной vision-language модели, отправляет ввод через Windows API и сохраняет эпизодический опыт в SQLite.

## Реализовано

- CLI-агент и локальная веб-панель на FastAPI.
- Профили игр, ограниченные навыки, режим сухого прогона и симуляционная среда.
- Локальные клиенты VLM и детектора целей.
- SQLite-память, телеметрия запусков и визуальная проверка отдельных результатов.
- Аварийная остановка F12 и ограничения для действий агента.

## Ограничения

- Проект не подтверждён как универсальный агент для произвольных игр.
- Результаты визуальных моделей и эвристик могут быть ошибочными; проверка добавляет задержку.
- Обучения весов модели нет.
- Для реального управления нужны Windows, выбранное игровое окно, настроенная локальная модель и отдельное окружение детектора для соответствующего навыка.
- Веб-панель по умолчанию доступна только на `127.0.0.1`; у панели нет собственной авторизации. Не открывайте её в недоверенной сети.

## Профильные условия для добычи (2026-11-16)

Аудит универсальности выявил, что CameraGuard требовал ровного pitch и подтверждённой опоры при любом action `mine`, а `OmniAgent` всегда делал отдельный preflight VLM. ## Применимость примеров памяти к текущему экрану (2026-11-16)

Подтверждённые skill-примеры раньше извлекались по игре, навыку и цели, хотя prompt требовал совпадения с текущим видимым состоянием. Добавлена nullable колонка `state_hash`; на planning frame вычисляется тот же 64-bit dHash, что используется эпизодической памятью, и runtime-summary выдаёт пример только при расстоянии не более 4 бит. Более поздний failure в близком состоянии скрывает предыдущий recipe этого состояния; успешная запись в другом контексте его не вытесняет. Проверки временной SQLite покрывают совместимое additive-расширение и разные состояния. Исторические строки без state hash остаются в статистике, но больше не доступны как применимый пример. Полный прогон: 261 тест unittest; pyflakes без замечаний. Живая полезность dHash-порога и его влияние на переиспользование не измерены.

Дополнительный аудит нашёл ошибку контекста для многошагового плана: исход каждого шага наследовал hash стартового кадра плана, даже если экран изменился после предыдущего шага. Теперь hash снимается со свежего кадра непосредственно перед каждым skill и перед каждым локальным recovery skill; кадр также переиспользуется в dry-run detector preview и начальной проверке результата. Новый регрессионный тест подтверждает раздельную привязку двух шагов к двум экранам. После исправления полный набор прошёл: 262 теста unittest; pyflakes без замечаний. Дополнительные захваты экрана не профилировались, live-эффект не измерен.

## Проверка переходов между шагами плана (2026-11-16)

## Ошибка emergency key monitor останавливает ввод fail-closed (2026-11-18)

Review `EmergencyHotkey._run()` обнаружил `except Exception: pass` вокруг key-state poll: постоянная ошибка чтения оставляла игру активной без клавиатурного stop-канала и без диагностики. Теперь polling-ошибка логируется отдельно, немедленно вызывает аварийное освобождение ввода и завершает цикл с `emergency_hotkey_error`; причина доступна в dashboard и run metadata. При аварийной финализации `release_all()` выполняет повторную попытку, а диагностическая ошибка release очищается, если retry успешен. Синтетические тесты покрывают отказ API, fail-stop callback и запись termination reason. Полный набор: 325 unittest прошли; pyflakes без замечаний. Живой ввод и отказ `GetAsyncKeyState` на активном desktop не проверялись.

Дополнительная проверка обнаружила race при запуске: поток ранее был асинхронным, поэтому исполнитель мог получить управление до первого чтения клавиши. `EmergencyHotkey.start()` теперь выполняет synchronous initial poll до создания потока; уже нажатый F12 вызывает stop без запуска monitor thread. Последующие опросы остаются фоновыми. Регрессии покрывают ошибку initial poll, ошибку worker poll и нажатие на старте. После этой правки полный набор: 327 unittest; pyflakes без замечаний.

## Убран лишний VLM-вызов при geometry-подтверждении выбранного мира (2026-11-18)

`VisionBrain.assess()` повторно сравнивал до/после через VLM для профильно распознанного выбора строки мира, хотя затем заменял все его результатные поля screen-geometry доказательством и отдельно вызывал `_inspect_menu(after)`. Теперь при одновременном выполнении всех условий адаптера отправляется только независимый after-state inspection; он остаётся обязательным, а timeout ограничивается остатком бюджета проверки. Unit/replay-тест измеряет снижение `2 → 1` VLM request, сохранение `screen_geometry` postcondition и обычный VLM fallback при отсутствующих координатах. Аудит этой же границы нашёл возможное ложное завершение: общий goal gate принимал `result="progress"` без `menu_action_succeeded=true`, а unusable independent inspection не снимал уже назначенный `progress`.
