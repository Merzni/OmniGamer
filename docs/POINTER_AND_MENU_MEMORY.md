# Указатель бота и память меню

Изменения 2026-11-14. Режим игры остаётся непрерывным, обязательных пользовательских целей нет.

## Отдельный указатель

По разрешению владельца после разбора 42 шагов по умолчанию `input_backend=native`: полноценная относительная камера использует общий SendInput, AI-маркер остаётся. Режим `window` доступен отдельно; `look` в нём теперь явно отклоняется вместо имитации движения маркера. `WindowInputController` отправляет WM_MOUSEMOVE, кнопки мыши и клавиши через PostMessage непосредственно HWND. Координаты принадлежат логическому указателю бота, системные SetCursorPos/SendInput/SetForegroundWindow не вызываются. Аварийный угол по-прежнему проверяется по настоящей мыши владельца.

`BotPointer` хранит координаты/кнопку/состояние нажатия. `DesktopPointer` рисует розовый круг с AI в отдельном прозрачном topmost-окне, не принимающем фокус и клики. WDA_EXCLUDEFROMCAPTURE исключает маркер из снимков VLM. Если исключение недоступно, desktop-маркер отключается с ошибкой в state, маркер панели остаётся. Живой JPEG панели получает собственный оверлей уже после захвата; модель его не получает.

Это оконный ввод, а не второй аппаратный HID. Raw Input/DirectInput и захват курсора игрой не изолированы: Minecraft может игнорировать сообщения, ограничивать относительный поворот или самостоятельно управлять общим курсором. Для одновременной независимой работы с полноценной 3D-игрой нужна отдельная Windows-сессия/VM; проект её не создаёт. Скрытый native fallback отсутствует. Режим `native` явно использует прежний общий SendInput с foreground-проверками.

Захват остаётся экранным MSS. В window-режиме игра должна быть видима и не свёрнута; проверяются девять точек перекрытия окна, это выборочная проверка, а не доказательство отсутствия любого перекрытия. Перекрытие останавливает шаг вместо принудительной фокусировки. Native сохраняет прежние проверки foreground/геометрии/отпускания ввода.

Настройки: `input_backend`, `desktop_bot_pointer`; CLI `--input-backend window|native`; панель/POST `/api/input-backend` с `{"backend":"window"}`. Переключение синхронизировано с шагом; UI останавливает автоцикл, само переключение игру не запускает. Выбор backend действует до рестарта процесса, после рестарта используется config.

## Попробовать, проверить, запомнить, повторить

1. Акторная VLM определяет scene_type, menu_id, menu_state, target_label и expected_result и предлагает действие.
2. После click/double_click/key в меню отдельный критик сравнивает before/after и увеличенные кнопки. Только usable-оценка (confidence ≥ 0.85, evidence ≥ 8 символов) с menu_action_succeeded=true и изменившимся состоянием создаёт кандидата.
3. Перед следующим действием новый кадр проверяется ещё раз (`menu_confirm`); назначение должно совпасть. Разные check IDs и оба доказательства сохраняются. Loading→gameplay разрешено как подтверждение загрузки.
4. SQLite-таблица `menu_actions` сохраняет game_id, состояния, действие, визуальный якорь кнопки, счётчики и ссылки на проверки. Неподтверждённый кандидат живёт только в RAM, после рестарта теряется.
5. При новом посещении меню нужна уверенность распознавания ≥0.85, совпадение состояния, пропорций изображения и локального якоря кнопки (RGB thumbnail и границы). Изменённая/заблокированная кнопка отклоняется. Выбранный/невыбранный мир — разные состояния, неизвестный выбор не распознаётся как знакомое состояние.
6. По сохранённому графу ищется путь до gameplay до четырёх рёбер, иначе одиночный знакомый переход. Выполняется только первый шаг; затем новая проверка. Метки delete/quit/exit/удал/выход исключены из автоматического повторения.
7. Ошибка повторения/неподтверждённый результат отключает ребро. Новое успешное освоение может его восстановить. Каждый профиль памяти отдельный; используйте одинаковый game_id в следующих запусках.

Визуальная модель остаётся ненадёжной: это две проверки одной моделью, не независимая истина и не доказанный причинный навык. Ошибки распознавания могут мешать обучению. При противоречии выборки отклоняются, а не объявляются успехом. Веса модели не обучаются. Предыдущие experiences и журнал сохраняются, новая таблица добавляется аддитивно.

## Проверки

Тесты памяти используют временные БД; устройства/модель подставляются. Проверяются перезапуск, цепочка из нескольких переходов с исполнением одного, смена внешнего вида кнопки, профиля/выделения, низкая уверенность, отключение неудачного повтора и полный агентный цикл. Отдельные тесты оконного контроллера запрещают вызовы системного ввода и проверяют клиентские координаты/отпускание клавиш.

Ручной безопасный smoke: собственное невидимое Win32-окно получило адресованные mouse down/up; реальная игра не управлялась. Розовое overlay-окно создалось, стало видимым и скрылось без ошибок, системный ввод не отправлялся. Полный игровой прогон оконного backend не выполнен.

Локальная VLM на простом искусственном меню подтвердила переход в gameplay двумя оценками по 0.9; временная БД сохранила и извлекла действие. На исторической паре Minecraft она ошибочно определяла выбранный мир в первой проверке, а в следующей давала другое/неизвестное выделение: переход корректно отклонён. Устойчивое самостоятельное освоение меню Minecraft пока не подтверждено.

## Исправления после реального запуска (2026-11-14)

Владелец разрешил общий ввод для игры. Native выбран стартовым режимом, без автоматического fallback. Native look теперь ставит AI-маркер в центр; после действия camera_feedback сопоставляет три области сцены (без HUD) и сообщает shift_observed/unconfirmed. Это эвристика, не градусы, не игровое достижение и не автоматическая остановка. Она может пропустить поворот при однотонном виде/большом смещении или ошибиться при иных изменениях сцены. Фокус и геометрия проверяются по-прежнему.

HTTP-ответы акторной модели, локализатора и критика ограничены JSON schema llama.cpp. Актор должен вернуть scene_type/camera_pitch/visual_confidence/menu_id/menu_state/target_label/expected_result и краткие observation/intent/commentary; пропуск обязательного поля или усечённый JSON останавливает шаг до ввода. Старый tolerant parser оставлен для отдельных совместимых вызовов, HTTP-путь не извлекает из оборванного JSON случайный клик.

Перед click/double_click ground_click заново локализует цель. ui_grounding.py выделяет кандидаты прямоугольных серых кнопок из пикселей, модель видит нумерованные области и увеличенные вырезки. Используется измеренный центр выбранной области; для иной формы допустим проверенный bbox с высокой уверенностью. Неопределённая/отключённая цель отклоняется. Это дополнительный VLM-запрос, поэтому скорость решения может снизиться.

Специальный экранный адаптер распознаёт раскладку Minecraft world_select: группу нижних кнопок, яркость/текст Play и прямоугольную рамку строки. При наличии видимой записи и отключённом Play выбирает измеренную строку существующего мира; после выделения — активный Play. Координаты/рамки вычисляются по текущим пикселям, внутренний API игры не используется. Это ограниченный адаптер данной раскладки, не универсальная поддержка списков всех игр. В иной раскладке возвращает неизвестность.

После меню-клика выполняется критик даже при scene_type=unknown. Успешный результат дополнительно читается отдельным запросом без переданного намерения; подтверждение следующего наблюдения также не получает рассказа акторной модели. Для перехода no_selection→world_selected есть явное экранное доказательство: рамка появилась и Play включился, клик лежит в измеренной строке; evidence_source=screen_geometry. После него нужна отдельная новая проверка с моделью/геометрией. Источник отображается честно, это не две независимые проверки VLM. Общие play_lessons и правила проверки игрового прогресса не заменяются одной дельтой кадра.

Лимиты HTTP: актор не менее 384 токенов, критик 768, компактный инспектор меню 384; требуется поддержка response_format/json_schema локальным сервером. Миграция БД аддитивная, evidence_source хранится внутри assessment JSON. Обучения весов нет.
