# Среда, запуск и проверка

Требуется Windows и Python 3.11. Создайте виртуальное окружение `.venv` в корне проекта. Прямые зависимости приложения зафиксированы в `requirements.txt`; `requirements-dev.txt` подключает их и `pyflakes`; `requirements-detector.txt` описывает отдельное окружение OWLv2 (PyTorch ставится под фактическую CUDA/CPU конфигурацию). Регрессионные тесты находятся в `tests/`.

## Зависимости

Прямые сторонние зависимости по импортам и установленные версии:

| Пакет | Версия в текущей .venv | Использование |
| --- | --- | --- |
| fastapi | 0.162.5 | HTTP-панель |
| uvicorn | 0.54.0 | Сервер |
| pydantic | 2.14.3 | Конфигурация и модели |
| pillow | 13.0.0 | Изображения |
| numpy | 2.4.6 | Хэши/дельта |
| mss | 10.2.0 | Захват экрана |
| pywin32 | 312 | Windows API |
| requests | 2.34.2 | VLM HTTP |
| rich | 15.0.0 | Консольные реплики |

Версии соответствуют текущей `.venv`; это прямые зависимости приложения, а не полный lock-файл транзитивного дерева. SQLite и ctypes входят в Python. PyTorch/CUDA не импортируются приложением: GPU-инференс выполняется отдельным llama-server. Frontend не требует Node/npm.

Dev-проверка неопределённых имён и неиспользуемых импортов: `.\.venv\Scripts\python.exe -m pyflakes omnigamer tools tests run_agent.py run_dashboard.py`. Полный набор регрессий: `.\.venv\Scripts\python.exe -m unittest discover -s tests -v`.

Точки входа `run_agent.py`/`run_dashboard.py` и `tools/summarize_run.py` переводят stdout/stderr в UTF-8 с заменой неподдерживаемых символов при наличии `reconfigure`. Не задавай `PYTHONIOENCODING` и не меняй code page ради запуска. При ошибке CLI/dashboard финализируют телеметрию и сохраняют короткую причину в `run_meta.json`.

CLI режимы выбираются явно: `run_agent.py --goal "..."` строит строгий план и исполняет реестровые навыки; `--dry-run` пишет `would_send` без ввода и использует временную SQLite `:memory:`; legacy-цикл запускается через `--legacy`. Для replay без окна укажи `--frame-dir <folder>` вместе с `--goal --dry-run`. Read-only диагностика: `python -m omnigamer.doctor --profile <path>` или `--game-id <id> --window <title>`. Doctor проверяет доступ к активному Windows input desktop через `OpenInputDesktop`; `SendInput` не вызывается. `start_all.bat` читает `OMNIGAMER_LLAMA_SERVER`, `OMNIGAMER_VLM_MODEL`, `OMNIGAMER_VLM_PROJECTOR`, необязательно `OMNIGAMER_DETECTOR_PYTHON`; `stop_all.bat` сверяет идентичность процесса перед остановкой.

Телеметрия хранит максимум 100 run-каталогов или 5 ГБ по умолчанию; старейшие завершённые прогоны удаляются при старте следующего run. Измените `telemetry_runs_max_count`/`telemetry_runs_max_mb` в конфиге, если требуется другой срок хранения.

Look задаётся как направление `left/right/up/down` и величина `small/medium/large`; значения мышиных counts определены в `omnigamer/look.py`. Старые x/y в строках SQLite остаются историческими данными, но новый VLM JSON с look x/y не принимается. Невалидный look повторяется один раз, затем превращается в отказ-safe wait. Look/wait получают статус `camera_motion`, исключены из мотивирующих записей памяти и не проверяются отдельным VLM-вызовом, если `assess_look_with_vlm=False`. `--goal` и поле панели добавляют короткую цель в отдельный блок prompt и run metadata. `prompts.jsonl` хранит фактически подмешанный контекст; `steps.jsonl` сохраняет сырой JSON до разбора, итоговое решение и длительности запросов по типам.

Повтор кадров: `state_repeat_detection_enabled=True`, окно `state_repeat_window=8`, dHash distance ≤4; telemetry показывает `state_repeat`, `repeat_of_step`, `look_oscillation`. Совпадение или look A-B-A-B запускает имеющуюся короткую стратегию восстановления. Это эвристика, не семантическое распознавание игровой ситуации.

## Запуск из корня проекта

Профили игры загружаются из `data/profiles/<game-id>.json`; явный файл можно указать через `--profile`. Например, `--game-id minecraft` выбирает `data/profiles/minecraft.json`, а `--profile path\to\profile.json` загружает пользовательский профиль и требует совпадения `game_id`, если он также передан. Dashboard тоже ищет профиль по `game_id` при attach, но не принимает произвольный путь. Неизвестный `game-id` получает общие значения по умолчанию. Проверяй схему без запуска игры:

```powershell
.\.venv\Scripts\python.exe run_agent.py --help
.\.venv\Scripts\python.exe -c "from omnigamer.profiles import load_profile; print(load_profile('minecraft').model_dump(exclude={'comment'}))"
```

`data/profiles/_template.json` показывает поля профиля. `motion_limits`, `actions`, `thresholds`, `regions`, запреты и движения используются goal- и legacy-путями; планировщик получает допустимые `actions`/`regions` как schema enum и повторно проверяет их до исполнения. В CLI `--goal` `motion_limits.max_actions` — общий на один запуск жёсткий лимит вызовов клавиатурного/мышиного/камерного ввода (`press_key`, `press_keys`, `hold_mouse`, `move_camera`); `release_all` не расходует лимит. Максимум вызовов навыка задаётся отдельно `goal_max_skill_steps`. Фактический input-счётчик и предел пишутся событием `input_action_budget` в `goal_steps.jsonl`. `motion_limits.interaction_retry_step_seconds` задаёт шаг вперёд между неудачными повторами `interact_until_change` (default 0.25 с); значение 0 сохраняет прицел на том же объекте и не отправляет дополнительный ввод. Minecraft задаёт 0, чтобы удержания добычи не сбивали прицел. `approach_target` читает `camera_counts_per_radian`/`invert_horizontal` из profile calibration, когда нет сохранённой per-game калибровки, и `approach_track_max_center_shift` из профильных thresholds (общий default 0.35; Minecraft профиль 0.2): рамка с большим скачком считается потерей цели, чтобы навык не переключался на соседний объект. Live телеметрия показала повторные сдвиги около 0.185; предел 0.1 часто обрывал слежение, поэтому профильное значение уточнено до 0.2. Один калиброванный поворот сдвигал рамку примерно на 0.034. `approach_target` для успешного достижения также требует, чтобы рамка цели покрывала перекрестие с профильным margin (default 0.05, Minecraft 0.08); около достижения выполняется bounded vertical/horizontal camera alignment. Это пока не даёт точного распознавания блоков в сценах с перекрытием или склоном. Глобальные `look`/`turn` используют дискретные counts без этого масштаба. Это прототип архитектурной переносимости, не доказательство поддержки произвольной игры.

В `--goal` при причинах `approach_target: blocked_after_side_step` и `target_not_reacquired` исполнитель делает одну локальную восстановительную цепочку перед VLM перепланированием: поворот до 60 counts (не выше `max_turn_counts` профиля), `search_target(sweep=2)`, новый `approach_target`. Сам навык при повторном плато один раз выполняет профильный `jump`+forward, затем одну боковую коррекцию в противоположную сторону; запрещённые клавиши и длительность проверяются до ввода. Всё ограничено общим лимитом ввода/навыков/времени и F12. Живой jump дал рост рамки 0.294, но дальнейшее наведение израсходовало лимит; цель не достигнута.

Доступные функции каталога навыков: `default_registry()` из `omnigamer.skills.registry`. Тесты навыков используют синтетические кадры и fake capture/detector/controls; запуск игрового цикла или отправка ввода не требуется. Для вызова `SkillSpec.executor` передай `recorder` либо объект run telemetry, иначе исполнитель завершится до первого ввода.

```powershell
# Справка; не выполняет игровых действий
.\.venv\Scripts\python.exe run_agent.py --help

# Перечень окон; без управления вводом
.\.venv\Scripts\python.exe run_agent.py --list

# Запуск панели, без автоматического начала игры
.\.venv\Scripts\python.exe run_dashboard.py

# Явный bind на интерфейс (по умолчанию localhost)
.\.venv\Scripts\python.exe run_dashboard.py --host 127.0.0.1

# РЕАЛЬНОЕ управление игрой: запускать при соответствующей задаче
.\.venv\Scripts\python.exe run_agent.py --window "Minecraft" --game-id "minecraft-survival" --steps 10

# Отдельный детектор и ограниченный навык (реальное управление; только по отдельной задаче)
start_detector.bat
.\.venv\Scripts\python.exe run_agent.py --window "Minecraft" --game-id minecraft --skill approach_target --target "a tree trunk"
```

Detector service использует отдельное окружение с OWLv2 и слушает только loopback `127.0.0.1:8082`; основной `.venv` и `requirements.txt` не содержат PyTorch/Transformers. Путь к Python детектора можно задать переменной `OMNIGAMER_DETECTOR_PYTHON`. `start_detector.bat` использует FP16 по умолчанию; для FP32 задайте `$env:DETECTOR_PRECISION='--fp32'`. Навык `--skill approach_target` требует `--window` и `--target`, не вызывает VLM и не пишет опыт SQLite; ограничения описаны в [SKILLS.md](SKILLS.md). Сухой прогон анализирует сохранённые кадры и не проверяет реальное управление.

Панель по умолчанию слушает `127.0.0.1:8765`, reload выключен. Другой bind задаётся аргументом `--host`, например `--host 0.0.0.0` для всех интерфейсов. Авторизации в панели нет; внешний bind открывает API управления игровым ПК доступным по сети клиентам. `start_dashboard.bat` запускает localhost-вариант и определяет корень проекта относительно собственного расположения.

Для отдельного запуска VLM задайте `OMNIGAMER_LLAMA_SERVER`, `OMNIGAMER_VLM_MODEL` и `OMNIGAMER_VLM_PROJECTOR`, затем запустите `start_qwen.bat`. При необходимости добавьте каталог CUDA DLL через `OMNIGAMER_CUDA_DLL_DIR`. Сервер привязывается к `127.0.0.1:8081` с alias `qwen3.5-4b-local`. Пути к исполняемому файлу и GGUF задаются на машине пользователя и не хранятся в репозитории.

Профильный флаг mine_requires_target_at_crosshair по умолчанию выключен. При включении отдельный локальный visual preflight должен вернуть target_at_crosshair=true: намеренная видимая цель занимает точный центр изображения (50%, 50%). False, null, низкая уверенность или ошибка проверки заменяют добычу на wait. Проверка использует только экранный кадр и не вызывает игровое API. Это оценка той же VLM, возможны ошибки и дополнительные задержки; она не подтверждает успешное разрушение блока. Включайте настройку только в профиле игры с такой механикой.

## Проверки при изменениях

Телеметрия включена по умолчанию; формат, ограничения кадров и чтение сводки: [TELEMETRY.md](TELEMETRY.md). Сводка одного каталога: `.\.venv\Scripts\python.exe tools\summarize_run.py data\runs\<run_id>`; без аргумента берётся последний прогон. В тестах телеметрию отключай или направляй в временный каталог.

Регрессии памяти, исполнения, парсера, preview и supervisor (временные БД, fake capture/controls/VLM/Windows, без ввода в рабочий стол и без сетевых запросов):

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Полный статический анализ: `.\.venv\Scripts\python.exe -m pyflakes omnigamer tools tests run_agent.py run_dashboard.py`.

Проверяются миграция и сохранность строк, изоляция игр, восстановление после перезапуска, fuzzy-поиск и коллизии, ограничение контекста, VLM payload, перепланирование повторов (включая анимированный фон), null duration, отказ фокуса, изменение геометрии, thread-local MSS, отказ SendInput и отпускание клавиш/мыши при исключении.

Дополнительно проверяются одновременные направление+Space и отпускание всех клавиш при исключении, знаковые относительные пакеты камеры, короткая длительность движения, навигационное перепланирование и независимый read-only preview без фокусировки/вызова шага.

Для legacy-цикла: action_delay_seconds=0.1, max_motion_seconds=0.75, image_max_size=640, vlm_max_tokens=192. Общий HTTP timeout — 110 с: ранее измеренный goal-планер занимал 56.72–74.82 с, среднее 61.34 с. После live timeout вывод ограничен `goal_plan_max_tokens=256` (строгая schema и отказ без ввода сохраняются); на сохранённом Stage 8 кадре получен валидный трёхшаговый план за 86.06 с. Goal-планы ограничены шестью шагами; профильные действия/регионы входят в схему. В панели целевой интервал 1 или 0.5 с — это нижняя цель, а не гарантированный timeout модели. Живой кадр обновляется отдельно раз в 0.5 с. Смотри фактические timings: vision_seconds, action_seconds, total_seconds.

Dry-run позволяет проверить планирование и детектор на кадрах без отправки игрового ввода. Для реального игрового прогона нужны выбранное окно и локально настроенные сервисы; результаты ограниченного прототипа не подтверждают универсальность.

Если VLM не разобрал ответ или не смог уверенно локализовать цель, ввод не выполняется. Авто-режим панели и CLI продолжают после видимого сообщения с паузой 1/2/4/8 секунд; остальные ошибки ввода и F12 останавливают цикл. Одиночный шаг панели по-прежнему возвращает ошибку, не начиная автоматические повторы.

Измерение 2026-11-13: один локальный VLM-запрос по сохранённому кадру с новым компактным prompt/640 px занял 2.309 с (88 токенов ответа). Это единичный замер без игрового ввода, не гарантия скорости. Даже при target=500 мс решения будут реже, если модель отвечает дольше.

С 2026-11-14: проверка результата по двум кадрам выполняется обычно раз в 4 шага, после копания/защиты камеры, при подтверждении нового опыта и во время восстановления. Она получает два кадра и два HUD-кропа, добавляет задержку (в одном офлайн-прогоне 3.87 с), отдельно измеряется verification_seconds. Перед копанием нужна уверенная отдельная оценка позы/опоры. Контракт: [CONTINUOUS_PLAY.md](CONTINUOUS_PLAY.md).

Тесты PlaySupervisor проверяют непрерывное продолжение после достижений, многократных восстановлений и загрузки старого остановленного плана; парные доказательства для нового опыта; отсутствие награды за неизменную картинку и рост ресурса при регрессии. Настройки: verification_interval=4, recovery_after_steps=20, recovery_after_seconds=90. Порог застревания запускает смену стратегии, а не остановку; API/селектора обязательной цели больше нет. Исторические тесты GoalSupervisor оставлены для проверки совместимости старых записей.

Миграция рабочей БД выполняется при следующем создании OmniAgent (например, после перезапуска панели). Старые строки останутся в legacy. В панели задай одно стабильное имя профиля для одной игры/режима и нажми привязку; при следующих запусках используй то же имя. Без имени идентификатор зависит от заголовка окна.

Для документации достаточно проверки ссылок и сверки описания с исходниками. Проверить синтаксис Python без импорта модулей, захвата экрана, записи pyc и отправки ввода:

```powershell
@'
import ast
from pathlib import Path
files = sorted(Path('omnigamer').rglob('*.py')) + [Path('run_agent.py'), Path('run_dashboard.py')]
for path in files:
    ast.parse(path.read_text(encoding='utf-8-sig'), filename=str(path))
print(f'Python syntax OK: {len(files)} files')
'@ | .\.venv\Scripts\python.exe -
```

Для изменения парсера проверяй raw JSON, markdown, синонимы и невалидный ответ без HTTP. Для memory используй `tempfile.TemporaryDirectory()` и отдельный путь к SQLite; не инстанцируй OmniAgent ради такого теста. Для изменений API можно подставить fake agent/capture/controls до lifespan/startup; обычный startup открывает рабочую БД, а первый шаг создаёт настоящий захват.

Полный игровой прогон требует выбранного окна, VLM и контроля реального ввода. Статическая проверка его не заменяет. Не запускай auto-play только ради проверки документации.

## Диагностика

- VLM: `data/last_vlm_raw.log` — последний ответ; `data/last_error.log` — последний traceback, если удалось записать. Это перезаписываемые файлы, не журнал всех запросов.
- Ошибка клиента VLM теперь прерывает шаг с HTTP 409 и подробностью в last_error вместо повторения fallback wait. Доли координат вроде x=0.5,y=0.6 автоматически преобразуются в 500,600 для клика; новое look x/y не принимается — направление и величина обязательны.
- Пустой кадр панели до шага ожидаем: привязка окна сама не сохраняет last_frame.
- Неэффективный клик может означать слишком малую дельту, неверный фокус, перекрытие окна или ошибку координат; не обязательно отсутствие эффекта в игре.
- Неотзывчивость при запросе может длиться до HTTP timeout; глобальной отмены запроса нет.
- `emergency_key` (по умолчанию F12) глобально опрашивается на текущем Windows desktop через `GetAsyncKeyState` каждые 10 мс. Срабатывание защёлкивает остановку, выставляет `is_running=False` и посылает up-события для клавиш/кнопок, которые удерживал контроллер. Вызовы VLM выполняются в daemon worker: агент прекращает ожидание почти сразу, но уже отправленный HTTP-запрос на сервере не отменяется. Опрос может не работать на secure desktop/экране входа, в другой Windows-сессии или при отказе Windows API; обычный foreground приложения не мешает. Failsafe курсора `x <= 5, y <= 5` остаётся отдельным механизмом.
- Ошибка `Game window lost focus` означает отказ проверки foreground: выведи выбранную игру вперёд и повтори шаг. При перемещении/resize во время инференса нужна новая попытка с актуальным кадром. Отказ SendInput отображается отдельной ошибкой; он не доказывает конкретную причину (например, разницу привилегий).
- После изменения исходников перезапусти run_dashboard.py/start_dashboard.bat и обнови страницу панели на втором ПК: reload=False и старый JavaScript продолжают работать до перезапуска/обновления.

Не публикуй рабочую SQLite, кадры и сырые ответы модели как часть технической документации: они могут содержать содержимое рабочего стола.

## Отдельный ввод и память меню (2026-11-14)

По умолчанию `input_backend=native`: общий SendInput и фокус окна. `window` использует HWND PostMessage без системной мыши и focus; `look` в нём явно отклоняется. CLI принимает `--input-backend window|native`; панель имеет явный переключатель `/api/input-backend`. Настройка действует до рестарта, стартовое значение берётся из config. Для Raw Input/полноценной 3D-изоляции нужна отдельная сессия/VM. Захват требует видимой игры; native использует общую мышь. Подробный контракт: [POINTER_AND_MENU_MEMORY.md](POINTER_AND_MENU_MEMORY.md).

Клики/клавиши в меню вызывают отдельный post-критик; перед следующим действием — menu_confirm для кандидата. Критик меню получает кадры/кнопки до 960 px (обычная игровая проверка остаётся 512/640), поэтому задержка может увеличиться. Таблица menu_actions добавляется через GameMemory без изменения старых experiences. Тестировать на временных БД; системный ввод и приём сообщений реальной игрой не проверять обычным unittest.

Подтверждено 101 unittest и Node VM панели. Smoke с собственным скрытым Win32-окном подтвердил адресованную доставку mouse down/up без SendInput/SetCursorPos. DesktopPointer создал/показал/скрыл окно без ошибок. Модель по искусственному меню подтвердила сохранение/извлечение, по старым кадрам Minecraft дала противоречивое выделение — память отклонила переход. Игровой прогон window backend не выполнен.
